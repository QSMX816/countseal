# CountSeal Protocol Specification v0.1

Status: Draft (reference implementation available in [`demo/`](demo/))

## 1. Overview

CountSeal separates the **content decryption right** from the **metering verification right** in LLM API relay architectures:

- The **user** holds the only private key that can decrypt responses.
- The **provider** signs a *meter attestation* binding the token count to the request and content hashes.
- The **relay** verifies the attestation and bills by token count, but never sees plaintext.

Result: *billable but unreadable* relaying.

## 2. Roles

| Role | Trusts | Does not trust |
|------|--------|----------------|
| User | Provider with content (necessarily) | Relay |
| Relay | Provider's signature (via pinned public key) | User (can't fake counts) |
| Provider | — | Relay (can't read content) |

## 3. Cryptographic building blocks

| Purpose | Algorithm |
|---------|-----------|
| Attestation signature | Ed25519 |
| Key encapsulation | X25519 + HKDF-SHA256 |
| Content encryption | AES-256-GCM |
| Hashes | SHA-256 |

All binary fields are base64url (no padding) in JSON envelopes.

## 4. Keys

- Provider identity keypair: `(sk_p, pk_p)` — Ed25519, long-term. `pk_p` is pinned by user and relay (out-of-band fingerprint check).
- Provider request-receive keypair: `(sk_pr, pk_pr)` — X25519, static or rotated.
- User ephemeral keypair: `(sk_u, pk_u)` — X25519, fresh per request.
- `nonce_q` — 96-bit random request identifier generated by the user.

## 5. Message formats

### 5.1 Sealed box (KEM/DEM envelope)

```json
{
  "v": 1,
  "kem": "<base64url X25519 ephemeral public key>",
  "nonce": "<base64url 96-bit>",
  "ct": "<base64url AES-256-GCM ciphertext>"
}
```

Sealing `plaintext` to recipient public key `pk`:

1. Generate ephemeral X25519 keypair `(e, E)`.
2. `shared = X25519(e, pk)`; `key = HKDF-SHA256(shared, salt="", info="countseal-v1")`.
3. `nonce` random 96-bit; `ct = AES-256-GCM(key, nonce, plaintext, aad)`.
4. Output `{v:1, kem: E, nonce, ct}`.

Unsealing uses `(E → shared)` with recipient private key. The `aad` (optional) binds context strings such as `"request"` or `"response"`.

### 5.2 Request envelope (user → relay → provider)

```json
{
  "v": 1,
  "pk_u": "<base64url>",
  "nonce_q": "<base64url 96-bit>",
  "sealed_prompt": { "...": "SealedBox to pk_pr, aad=\"request\"" }
}
```

### 5.3 Response envelope (provider → relay → user)

```json
{
  "v": 1,
  "sealed_response": { "...": "SealedBox to pk_u, aad=\"response\"" },
  "sealed_k":      { "...": "SealedBox wrapping the symmetric content key k to pk_u" },
  "meter": {
    "v": 1,
    "model_id": "example-model",
    "n": 1234,
    "h_R": "<base64url SHA-256 of response plaintext>",
    "h_C": "<base64url SHA-256 of sealed_response.ct>",
    "h_K": "<base64url SHA-256 of sealed_k.ct>",
    "nonce_q": "<base64url>",
    "ts": 1759480000
  },
  "attestation": "<base64url Ed25519 signature>"
}
```

Hybrid encryption: content is encrypted under a random symmetric key `k` (AES-256-GCM); `k` is sealed to `pk_u` as `sealed_k`. `sealed_response.ct = AES-256-GCM(k, nonce_c, R, aad="response")`.

### 5.4 Meter attestation

```
canonical = JSON.dumps(meter, sort_keys=True, separators=(",", ":"), ensure_ascii=False).encode("utf-8")
attestation = Ed25519.Sign(sk_p, canonical)
```

Field meanings:

- `n` — billed token count (prompt + completion, or completion only, per the billing policy).
- `h_R` — commits to plaintext, lets the user verify content integrity.
- `h_C`, `h_K` — commit to what was actually transmitted.
- `nonce_q` — binds the attestation to one request (anti-replay, anti-reuse).
- `ts` — UTC unix seconds.

## 6. Protocol flow

```
User                          Relay                          Provider
 | S1: (pk_u, sk_u) ← X25519;  nonce_q ← random
 | sealed_prompt ← Seal(pk_pr, prompt)
 |---- request envelope ------------------->|
 |                                          |---- forward ----------------->|
 |                                          |            S2: R, n
 |                                          |            k ← random
 |                                          |            C ← AES-GCM(k, R)
 |                                          |            K ← Seal(pk_u, k)
 |                                          |            meter; attestation ← Sign(sk_p, canonical)
 |                                          |<--- response envelope --------|
 |<--- response envelope -------|
 |                 S3: verify attestation (pk_p)
 |                 S3: nonce_q unused? ts within window?
 |                 S3: bill by n; forward envelope
 | S4: k ← Unseal(sk_u, sealed_k); R ← AES-Open(k, C)
 | S4: SHA-256(R) == h_R ? accept : reject+keep evidence
```

## 7. Verification rules

**Relay MUST reject (and not bill) unless all hold:**

1. `attestation` verifies under pinned `pk_p` over `canonical(meter)`.
2. `nonce_q` has not been seen before (relays keep a replay cache; TTL ≥ attestation validity window).
3. `|now − meter.ts| ≤ 300` seconds.
4. `n` is within the configured billing bounds (e.g. `1 ≤ n ≤ 10^6`).
5. `SHA-256(sealed_response.ct) == h_C` and `SHA-256(sealed_k.ct) == h_K`.

**User MUST reject unless:**

1. Attestation verifies under pinned `pk_p`.
2. `meter.nonce_q` matches the request's `nonce_q`.
3. `SHA-256(R) == h_R` after unsealing.

## 8. Security properties

| Adversary | Goal | Prevented by |
|-----------|------|--------------|
| Relay | Read prompt/response | Content sealed to user/provider keys; relay has no private key |
| Relay | Inflate bill | Attestation is provider-signed; relay can't alter `n` |
| Provider | Over-report `n` | *(optional, see §9)* ZK range proof over `n`; else `n` is trusted as provider-reported |
| User | Deny usage | Attestation signed by provider binds `nonce_q` and content hashes |
| Attacker | Replay old attestation | `nonce_q` replay cache + `ts` window |

Non-goals (v0.1): hiding usage volume from the relay; protecting against a compromised provider; traffic analysis resistance.

## 9. Optional extensions

- **ZK meter constraint**: provider attaches a range proof (e.g. Bulletproofs) that `n` is within bounds and consistent with a commitment to the tokenized length of `R`; relay verifies before billing. Prevents provider over-reporting.
- **Multi-relay audit chain**: each relay appends a forwarding signature over `(h_C, h_K, meter_hash, hop_id)`; the user can reconstruct the path.
- **Dispute settlement**: any party presents `attestation` + `R`; anyone can check `SHA-256(R) == h_R` to arbitrate billing disputes.

## 10. Versioning

`v` fields are integer. Additive fields MUST be ignored by old implementations; changing semantics requires a new `v`.
