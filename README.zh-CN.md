# CountSeal

**大语言模型 API 中转场景下，计费可验证的端到端加密协议。**
核心口号：*billable but unreadable* —— 中转站能计费，但看不到内容。

[English](README.md) · [协议规范](SPEC.md) · [参考实现](demo/demo.py)

## 解决什么问题

现在很多人通过 **API 中转站**（网关、代充、共享账号代理）调用大语言模型。中转站要在 HTTP 层按 token 计费，就必须解开 TLS、解析内容——于是你的 **提示词和模型输出对中转站完全明文可见**。

如果简单地把响应加密、本地解密，计费就崩了：中转站无法验证 token 数量，服务商可以虚报、用户可以抵赖，商业模式不成立。

## 核心思路

把两种权利拆开：

| 权利 | 谁持有 | 机制 |
|------|--------|------|
| 内容解密权 | **仅用户** | X25519 密封盒，只有 `sk_u` 能解 |
| 计量验证权 | **服务商签名、中转站验签** | Ed25519 计量证明 `{n, h_R, h_C, h_K, nonce_q, ts}` |

中转站只拿到响应密文 + 计量证明：验签、防重放、按 `n` 计费，全程无解密能力。用户本地解密后核对内容哈希 `h_R`，确认内容未被篡改、与计费凭据一致。`nonce_q` + 时间窗防重放，哈希把计量值绑定到实际传输的字节。

```
用户                        中转站                        服务商
 ── 密文prompt, pk_u, nonce_q ──▶── 原样转发 ──▶
 ◀── (C, K, meter, π) ── 验签π、按n计费 ── (C, K, meter, π) ──
 ── 解封 k、解密、核对 h_R ──
```

## 各方可见性

| | 提示词 | 响应内容 | token 计量 |
|---|---|---|---|
| 中转站 | 密文 | 密文 | 可验证 ✓ |
| 用户 | 明文 | 明文 | 可核验 ✓ |
| 服务商 | 明文 | 明文 | 已签名背书 ✓ |

## 快速体验

```bash
cd demo
pip install -r requirements.txt
python3 demo.py
```

单进程跑完三方全流程：密封提示词 → 服务商生成响应并签发计量证明 → 中转站验签计费（无法解密）→ 用户解密并核验哈希 → 最后篡改一个字节演示拒绝。

## 协议规范

见 [SPEC.md](SPEC.md)：消息格式（KEM/DEM 密封盒、计量证明规范化序列化）、验证规则、可选扩展（`n` 的零知识范围证明防服务商虚报、多级中转审计链、争议仲裁）。

算法：Ed25519 · X25519 + HKDF-SHA256 · AES-256-GCM · SHA-256。
